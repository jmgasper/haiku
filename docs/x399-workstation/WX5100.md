# Radeon Pro WX 5100

The X399's NVIDIA card was replaced with a WX 5100 on 2026-10-10. The
NVIDIA graphics and video results in STATUS.md describe the previous card,
not this installation. Full AMD acceleration is **not implemented yet**.

## Required result

The requested result is full GPU acceleration in air/OS, hardware media
decoding in both airTime and Summit, and installation and verification of
the resulting system on the X399. Device recognition, a driver that loads,
software rendering, or one engine self-test does not meet that result.

Work is on `wx5100`, in `/mnt/HaikuWork/x399/haiku-wx5100`, based on master
`75edf7a105`. This isolates it from the other device agents. The build is
`/mnt/HaikuWork/x399/build/wx5100`; evidence is outside git in
`/mnt/HaikuWork/x399/evidence/wx5100`. Use `x399/state/lab.lock` for target
mutations. SSH configuration is in `x399/ssh/config`; no credentials belong
in this document. The KVM's USB input is broken, so retain SSH/VNC and a
bootable system while bringing up the GPU.

| Desktop | `framebuffer` driver; logical 800x600 at 200 percent scaling |

The existing `radeon_hd` WX 5100 entry is inside a disabled block, along
with other newer cards. Enabling the PCI ID alone cannot supply command
submission, shaders, or video decoding. It also needs DCE 11.2 validation
before taking over the display.

The new driver exposes `/dev/dri/amdgpu/0`. Opening an uninitialized device maps
BAR5 read-only; queries return a versioned identity/register snapshot. Explicit
root-only lab operations can read the ROM and run a bounded SDMA test. They
temporarily allow kernel register writes under the driver mutex; applications
never receive raw MMIO or submit arbitrary command buffers. Client DMA startup
retains a writable kernel mapping for the executor. These operations
are not run at boot or on open, and do not advertise application acceleration.
The driver is built explicitly and is not yet included in release images.

## ROM and first engine bring-up

The native ROM reader succeeded through SMC index 11 after finding no ACPI
VFCT. It restores both indirect indices. The 256 KiB image has SHA-256
`e493c678733c3266ca2a7d4adc82d3749ed2ea59b5153b00730c43e5f8f12850`.
Its ATOM 1.5 VRAM usage table reports no fixed firmware reservation and
32 KiB of driver scratch. ROM images and firmware remain outside git.

The SDMA test validates the firmware container's lengths, IP/header versions,
alignment and jump-table bounds. This is structural validation, not a claim
of signature authentication. Host tests under ASan/UBSan passed all input
truncations, unaligned buffers, corrupt lengths/offsets and a synthetic ATOM
reservation above 4 GiB. Both Polaris SDMA firmware files passed the parser.
The SDMA0 lab image is version 58, feature 31, SHA-256
`e27b3ec976f87e32883b9190e653b20d27f9e77da8dd2d77eeb10c35ee9f1e61`.

`amdgpu_sdma` uses kernel-generated copy/fill/fence packets in a backed-up
1 MiB VRAM region at offset 32 MiB. The following 2 MiB is reserved for the
SMU workspace and firmware staging until a cold boot. It checks every active
head and cursor, the firmware reservation, ring ownership and the boot framebuffer first.
It polls with bounded timeouts and halts the engine before restoring memory.
This is a bring-up test, not the buffer allocator or submission API needed
by applications. The original direct microcode-loading experiment failed;
the driver now uses the protected SMU loader used by Linux for Polaris.

The first native attempt refused the test at preflight, before firmware or
ring writes. The firmware uses linear-aligned surfaces (`GRPH_CONTROL`
`0x0a10800a`), which the corrected check accepts alongside linear-general.
The second candidate reached submission but timed out after 500 ms: fence
zero, read/write pointers 0/96, engine status `0x46dc6452`. It halted the
engine and quarantined the test because the engine had not become idle.
There was no successful GPU execution at that checkpoint. Identity/reopen
tests passed afterwards. Evidence: `sdma-native-first.txt`, `sdma-native-second.txt`.
The second driver SHA-256 is
`47bd10b09994aebc5c9b1dffb4f56cc2307585bebf6d4c32f3a334646022ca92`.
The local build and isolated QEMU unsupported-device path passed; the next
investigation covered firmware loading and GMC access setup.
Cold power cycles are required for reliable lab restarts. A successful POST
can take about two minutes; a short SSH timeout does not establish a hang.

Setting the GMC physical VRAM aperture changed the SDMA status, but did not
produce execution. The diagnostic run recorded no VM fault, a zero SDMA

## Client buffers and asynchronous DMA

The native driver now owns a VRAM page allocator and persistent SDMA executor.
The first 64 MiB is reserved for firmware scanout and kernel rings/workspaces;
ATOM reservations and active cursors are also excluded. Buffer allocations
currently use the 256 MiB CPU aperture and are limited to 64 MiB each. The
allocator handles 64-bit VRAM offsets. At this checkpoint there were no
system-memory mappings; the next section records their implementation.
VRAM allocations outside the CPU aperture still need implementation.

Each open file has its own handles, monotonically increasing fences and
accounting. Client commands specify handles and bounded offsets; the kernel
constructs copy/fill packets and GPU addresses. A kernel worker executes jobs
in submission order, splitting large operations into SDMA packets. There are
at most 64 pending jobs per client and 256 for the device. Firmware startup is
root-only; ordinary clients can allocate, map, submit and wait afterwards.
Inherited file descriptors cannot issue commands from another team.

Mappings expose only that buffer, not the kernel command ring or registers.
Free/close revokes mappings and clones before VRAM reuse. Jobs retain buffer
and client references until completion, so closing a file cannot free memory
still in use by the GPU. A GPU failure stops new work and preserves affected
VRAM allocations until a cold boot. Hardware reset/recovery is not yet
implemented or qualified; this fault path is not a recovery claim.

Validation on X399 on 2026-10-10:

  The identity/reopen probe passed before and after (`buffers-preflight.txt`).

## System RAM and GPU page tables

The driver now sets up a 1 GiB flat GART in private VMID0, backed by a 2 MiB
VRAM page table at offset 16 MiB. GPU addresses `0x10000000..0x4fffffff`
translate to wired Haiku RAM pages. `AMDGPU_CREATE_SYSTEM_BUFFER` creates
system-memory BOs using the existing ownership, mapping, submission and fence
API. Each 4 KiB PTE is validated against VI's 40-bit physical-address limit
and is snooped, readable and writable, with execution disabled. The CPU
mapping remains cached. No userspace physical address or PTE is accepted.
The same copy/fill executor now supports both memory domains.

GART allocation accounting is separate from VRAM accounting. Completed jobs
release their references before RAM can be unmapped: the kernel clears PTEs,
flushes CPU page-table writes and invalidates the GPU TLB before returning
pages to Haiku. Mapping revocation or engine/translation failure retains the
RAM's kernel area and wiring until a cold boot. Deleting the area on a timeout
would incorrectly return pages to the OS. VM protection faults are checked
alongside SDMA completion, so a fence alone cannot hide a redirected fault.
This is a kernel DMA address space, **not** per-client shader GPUVM support.
There are no user-supplied command buffers yet.

## Implementation and acceptance work remaining

1. **Memory, firmware and execution:** own VRAM allocations without touching
   scanout or firmware reservations; extend the working GART and buffer
   ownership path with per-client GPU address spaces, validated firmware loading,
   interrupts and fences. Bring up SDMA copy/fill, then GFX8 graphics/compute
   and UVD6 video. Compare copy/fill results and guards, reject bad requests,
   test concurrent clients, teardown, timeouts, reset and reuse. A halted
   engine or a CPU-written success value is not execution evidence.
2. **Display and desktop:** native DCE 11.2 modesetting, all attached displays,
   cursor, retrace, hotplug and the fork's display layout/scaling API. Verify
   actual output, mode changes and repeated layouts; keep framebuffer
   recovery while qualifying. Accelerated 2D needs its own drawing tests.
3. **Mesa:** connect the native kernel interface to Mesa's AMD winsys.
   Evaluate RadeonSI and RADV/Zink against the fork's existing Haiku EGL and
   OpenGL Kit presentation paths. Require the AMD hardware renderer with no
   per-process environment, correct independent pixel readback, representative
   rendering tests, multiple windows, resizing/occlusion and sustained load.
   Keep software fallback functional when the device cannot initialize.
4. **Video and applications:** a UVD-backed Media Kit decoder with explicit
   codec/profile limits, capability discovery and reliable software fallback.
   Qualify H.264 and HEVC, including supported ten-bit paths, against software
   frame references; test reference pictures, reordering, seek, flush, stream
   changes and malformed streams. Add airTime's hardware-decoder selection
   entry only when that backend exists. Summit's file and MSE playback need
   both qualification and backend-specific capability handling. Require
   engine completion evidence, correct pictures/audio sync, and performance
   measurements in **both applications**. Do not advertise codecs the card
   cannot decode in hardware.
5. **Installed release:** package the driver, firmware (with licenses), Mesa,
   decoder and application changes; cross-build, QEMU smoke, commit and
   integrate, then install the current complete build on X399 with a tested
   rollback. Reboot and rerun graphics, display, airTime and Summit checks on
   the installed defaults. The goal remains open until all of this works.

Immediate next work: GFX8/UVD6 execution and per-client GPU address spaces,
then Mesa and the Media Kit decoder. Engine timeout/reset and reuse still
need qualification. VRAM allocations are limited to the CPU aperture; RAM
BOs now use GART. Manual firmware startup and release packaging remain open.
