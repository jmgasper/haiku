# Radeon Pro WX 5100

The X399's NVIDIA card was replaced with a WX 5100 on 2026-10-10. The
NVIDIA graphics and video results in STATUS.md describe the previous card,
not this installation. Full AMD acceleration is **not implemented yet**.

## Required result

The requested result is full GPU acceleration in air/OS, hardware media
decoding in both airTime and Summit, and installation and verification of
the resulting system on the X399. Device recognition, a driver that loads,
software rendering, or one engine self-test does not meet that result.

Work is on `wx5100`, in `/mnt/HaikuWork/x399/haiku-wx5100`, based on master
`75edf7a105`. This isolates it from the other device agents. The build is
`/mnt/HaikuWork/x399/build/wx5100`; evidence is outside git in
`/mnt/HaikuWork/x399/evidence/wx5100`. Use `x399/state/lab.lock` for target
mutations. SSH configuration is in `x399/ssh/config`; no credentials belong
in this document. The KVM's USB input is broken, so retain SSH/VNC and a
bootable system while bringing up the GPU.

## Verified starting point

On the X399 running hrev60206+805, the native `amdgpu` probe reports:

| Item | Observed value |
| --- | --- |
| PCI identity | `1002:67c7`, revision `00`, subsystem `1028:0b0d`, `42:00.0` |
| CPU VRAM aperture | BAR0 `0x80000000`, 256 MiB |
| Doorbell aperture | BAR2 `0x90000000`, 2 MiB |
| Registers | BAR5 `0x9f600000`, 256 KiB |
| VRAM | 8192 MiB, GPU physical base `0xf400000000` |
| Firmware framebuffer | CPU `0x80000000`, 1600x1200, stride 6400, 7,680,000 bytes |
| DCE heads | Heads 0 and 1 enabled, both scanning GPU `0xf400000000`, pitch 1600 |
| SDMA | Both F32 HALT bits set; SDMA0 ring disabled |
| UVD | STATUS and POWER_STATUS both zero; no decoder initialized or tested |
| Desktop | `framebuffer` driver; logical 800x600 at 200 percent scaling |

The existing `radeon_hd` WX 5100 entry is inside a disabled block, along
with other newer cards. Enabling the PCI ID alone cannot supply command
submission, shaders, or video decoding. It also needs DCE 11.2 validation
before taking over the display.

The new driver exposes `/dev/dri/amdgpu/0`. At this checkpoint it only maps
BAR5 read-only and returns a versioned identity/register snapshot. It does
not expose raw MMIO to applications, enable bus mastering, load firmware,
allocate GPU buffers, submit commands, or advertise acceleration. A query
does not alter the display or engine state. It is built explicitly and is
not yet included in release images.

Validation on 2026-10-10:

- Cross-build: `jam -q -j8 amdgpu amdgpu_probe` passed using the existing
  GCC 13.3 cross toolchain. Build logs are in the isolated build directory.
- Isolated QEMU x86_64 guest: the actual driver logged `no supported
  device`; `amdgpu_probe --expect-no-device` passed and userspace remained
  available. This proves only the non-AMD path, not GPU emulation.
- X399: identity queries, malformed size/version, invalid pointer, unknown
  operation, two simultaneous opens with one closed, and 32 reopen cycles
  passed. Evidence: `probe-20261010-pass.txt`. `screenmode -d` still reports
  the firmware display. The driver and probe were installed as non-packaged
  lab files; the system package has not been replaced for AMD support.
- Driver SHA-256 at this checkpoint:
  `9a432b2c0cdd350cf86714fe8893f69817f2d797df855a4e6a36e9af9fd51539`.
  Probe: `742e91281504790540a5b0dead083836aba11ff0e57996543e46f1e4090e21c2`.

The first candidate rejected this multifunction PCI device because it
compared the whole header type byte with zero; the driver now masks the
multifunction bit. The first native test also expected the internal
`B_DEV_INVALID_IOCTL` value, which the ioctl layer converts to `ENOTTY`.
Both observations are retained in the evidence directory.

## Implementation and acceptance work remaining

1. **Memory, firmware and execution:** own VRAM allocations without touching
   scanout or firmware reservations; GART/system-memory mappings, per-client
   buffer ownership and GPU address spaces, validated firmware loading,
   interrupts and fences. Bring up SDMA copy/fill, then GFX8 graphics/compute
   and UVD6 video. Compare copy/fill results and guards, reject bad requests,
   test concurrent clients, teardown, timeouts, reset and reuse. A halted
   engine or a CPU-written success value is not execution evidence.
2. **Display and desktop:** native DCE 11.2 modesetting, all attached displays,
   cursor, retrace, hotplug and the fork's display layout/scaling API. Verify
   actual output, mode changes and repeated layouts; keep framebuffer
   recovery while qualifying. Accelerated 2D needs its own drawing tests.
3. **Mesa:** connect the native kernel interface to Mesa's AMD winsys.
   Evaluate RadeonSI and RADV/Zink against the fork's existing Haiku EGL and
   OpenGL Kit presentation paths. Require the AMD hardware renderer with no
   per-process environment, correct independent pixel readback, representative
   rendering tests, multiple windows, resizing/occlusion and sustained load.
   Keep software fallback functional when the device cannot initialize.
4. **Video and applications:** a UVD-backed Media Kit decoder with explicit
   codec/profile limits, capability discovery and reliable software fallback.
   Qualify H.264 and HEVC, including supported ten-bit paths, against software
   frame references; test reference pictures, reordering, seek, flush, stream
   changes and malformed streams. Add airTime's hardware-decoder selection
   entry only when that backend exists. Summit's file and MSE playback need
   both qualification and backend-specific capability handling. Require
   engine completion evidence, correct pictures/audio sync, and performance
   measurements in **both applications**. Do not advertise codecs the card
   cannot decode in hardware.
5. **Installed release:** package the driver, firmware (with licenses), Mesa,
   decoder and application changes; cross-build, QEMU smoke, commit and
   integrate, then install the current complete build on X399 with a tested
   rollback. Reboot and rerun graphics, display, airTime and Summit checks on
   the installed defaults. The goal remains open until all of this works.

Immediate next step: implement firmware validation and a bounded SDMA ring
test, using the measured VRAM layout. Account for every active display and
ATOM firmware reservation before assigning scratch VRAM. The BIOS left the
system aperture bounds at zero; do not assume system RAM is GPU-addressable.

## Source references

- [Linux AMDGPU](https://github.com/torvalds/linux/tree/master/drivers/gpu/drm/amd/amdgpu):
  local reference `/mnt/HaikuWork/src/linux-6.18.52` (archive
  `/mnt/HaikuWork/cache/linux-6.18.52.tar.xz`). Relevant implementation is
  `gfx_v8_0.c`, `gmc_v8_0.c`, `sdma_v3_0.c`, `uvd_v6_0.c`, `vi.c`, and the
  Polaris SMU code in `../pm/powerplay/smumgr`. Check each source's license
  when adapting it. The register headers used for the snapshot are
  MIT-licensed and named in driver.cpp.
- [RadeonGfx](https://github.com/X547/RadeonGfx), inspected at
  `797e94775d274f243d8e0fe18b434b672bdeb768`, local `x399/src/RadeonGfx`:
  reusable Haiku integration ideas, but its units implement GFX6 and DMA1,
  not the WX 5100's GFX8/SDMA3. It is not a ready-made Polaris driver.
- Mesa in `src/forks/mesa`: the shared checkout belongs to other work too.
  Make a separate worktree for AMD changes. The AMD winsys currently has
  no Haiku implementation. Existing Haiku presentation code can be reused.
- airTime `src/engine/HardwareVideoDecoder.cpp` explicitly enumerates
  supported hardware add-ons. Summit's corresponding Media Kit selection
  lives in WebKit `Source/WebCore/platform/graphics/haiku`; supporting a new
  Media Kit decoder alone does not establish both apps select it correctly.
